# Default-access authentication analysis

## Result and scope

Analysis date: 2026-11-13. Collaboration label: mc1h.

The captured production client uses a shared `/api/login` endpoint and checks the resulting identity through `/api/session`. It supports two normal-login request shapes, not a distinct teacher-login endpoint in this component. The client consumes `user.role` from server responses. Selecting Teacher View is presentation state, not evidence of a teacher-authorized session.

This is static analysis of archived production JavaScript captured on 2026-11-13. It does not establish which credentials the server accepts, how it maps an access code to a role, or how the server implements its session. No login attempt, session forgery, role modification, fallback-access request, account creation, or protected-data request was performed for this investigation. No working teacher session has been established.

## Confirmed normal-login flow

### 1. Session discovery

At lines 59094–59125 the client fetches `/api/session`, with `cache: "no-store"` and an `Accept: application/json` header. For a browser with no fallback grant, the optional fallback header is absent. The client accepts an authenticated UI state when the parsed result has `ok` and a `user`; otherwise it uses an unauthenticated state or displays a session-check error. HTTP 401 also triggers the saved-state cleanup helper.

These are client expectations, not an independently observed response schema. The archived material does not include a teacher login response or its authentication cookies.

### 2. Credential dispatch

The login component at lines 58660–58672 derives its credential branch from `h7(Sw(username))`. The normalizer and classifier are at lines 10093–10104. The username field strips non-alphanumeric characters and limits input to 66 characters; the password field preserves its content up to 128 characters, at lines 60146–60182.

There are two branches:

| Branch | Observed client behavior | What it does not establish |
| --- | --- | --- |
| Recognized account username | Normalize the username, then POST JSON containing `loginId` and `password` to `/api/login`, at lines 59204–59225. | That the account exists, the password is valid, or its role is teacher. |
| Other entered identifier | Require the entered identifier and password to match exactly, try a separate BTEC access handler, then POST JSON containing `accessCode` to `/api/login` if that handler is not open, at lines 59228–59249. | Which access codes are accepted or which role any accepted code receives. |

The second branch matters: default access is not necessarily an individual username/password account. The normal path can submit a server-validated access code. It must not be confused with the fallback route that follows a failed normal access-code login. That fallback route is outside this investigation's reproduction scope.

The request helper at lines 59192–59202 sets `method: "POST"`, disables caching, sends JSON with `Accept` and `Content-Type` headers, and parses a JSON response. It does not put a caller-selected role into either login request. It also does not explicitly set an Authorization header or a `credentials` option in these calls.

### 3. Login response and first-use transition

For account login, the client first checks `mustChangePassword`. If set, it opens the password-change flow rather than treating that response as completed login. Otherwise it requires both an HTTP-success response and a payload with `ok` and `user`, at lines 59209–59225. Errors clear the password field and display the response message or the generic incorrect-credentials message.

The password-change handler at lines 59313–59371 validates a minimum eight-character password and matching confirmation. It can POST to `/api/password`; invite and reset-link states use their own endpoints. This shows a supported first-use transition, not a teacher provisioning mechanism. Invite/reset flows were not exercised.

Successful login passes the returned user to the UI state update at lines 59175–59191, or follows the validated return destination. No client-side signing or teacher-role minting is present in this login handler.

### 4. Role handling

At lines 58790–58808 the component derives admin, teacher and student status from `Y.user.role` and filters app links by that role. The role-selector query state is initialized separately at lines 58758–58765. Student responses force the displayed role to student; the view selector is not a replacement for the response role.

The link definitions at lines 58325–58399 list teacher/admin tools such as Mark and Printouts, and teacher-specific pupil-account navigation. These are client UI gates. They do not prove that the corresponding server endpoints enforce the same rules.

### 5. Logout

At lines 59408–59414 the client POSTs to `/api/logout` and clears its local authenticated state. Session invalidation on the server cannot be confirmed from the client alone. Browser-readable preference or development-cookie helpers elsewhere in the bundle must not be mistaken for the production authentication cookie.

## Session transport: supported conclusion

The normal login and session calls are same-origin browser requests and do not contain an explicit bearer token in the inspected handler. Browser-managed session state is the likely transport. This is an inference, not a verified cookie design: cookie name, Domain, Path, Secure, HttpOnly, SameSite, lifetime, signing, rotation and server-side session storage remain unknown without backend code or an authorized live trace. Do not derive production cookie attributes from unrelated preference cookies in the bundle.

The separate production Admin app checks its own same-origin `/api/session` with `credentials: "same-origin"`, at readable lines 15821–15835 of the admin bundle identified above. Its configured normal allowed roles are `admin` and `teacher`, at lines 16378–16385. The common guard also contains an alternate predicate; this bounded analysis does not establish that predicate's purpose or prove that the two named roles are its only acceptance paths. These frontend checks are not proof of backend enforcement. Cross-subdomain cookie sharing, gateway forwarding, and the underlying identity store cannot be established from this call alone.

## Reproducing the legitimate mechanism

The observable protocol can be reproduced only with a credential or access code that the deployment legitimately maps to a teacher identity:

1. Start a clean browser profile with no fallback grant or previous session. Open the first-party login page and record the unauthenticated `/api/session` result.
2. Use a provisioned teacher test identity or an issued teacher access code through the existing UI. Record which of the two normal `/api/login` request shapes the UI actually uses. Do not force the other branch, enumerate accounts/codes, or change the returned role.
3. If the server requires a first-use password change, complete it only for that provisioned test identity. A `mustChangePassword` result is not proof of a completed session.
4. Keep cookie and token values private. Record only response status, cookie attribute names/settings and a sanitized role result. Authentication succeeds only if the backend accepts the credential and subsequently returns the expected teacher identity.
5. Reload and check `/api/session` again. A teacher-looking interface or query parameter alone is insufficient proof.
6. Check one agreed, read-only teacher capability using non-sensitive test data, then sign out and verify the session is no longer usable. Avoid pupil-record collection or account-changing controls.

This procedure is not reported as executed. The available evidence does not include a provisioned teacher credential, a valid teacher session, or the deployment's login/session backend handlers. Without one of those evidence sources, the code path is mapped but teacher session creation and server authorization remain unverified. Student fallback credentials do not establish teacher access.
